# 0.9.9 变量证据恢复与原生世界书聚焦根修

## 真实失败

0.9.8 在全新真实聊天首轮完成了固定楼层写读和人物档案提交，但人工逐项复核发现两项假成功：正文把一件物品写成尚待领取，MVU 却已经把它放入背包；变量医生不仅漏掉该矛盾，还把原更新中对象类型的“效果”改成字符串。World 的轮次、保存与注入均成功，但模型只把玩家本轮设定改写进黑箱，事件、势力、风声和大势没有一项非玩家自主推进。因此该轮被拒绝，连续试跑仍为 0/12。

本机隐私安全取证只保留结构计数：Story Oracle 系统提示约 8.9 万字符，最终接受正文没有独立高显著度分栏；World 提示约 19.2 万字符，其中世界书约 15.5 万字符、Doctor 人物行动段约 1800 字。原始剧情、人物姓名和模型凭据不进入仓库。

## 成功语义

- 模型在唯一修复 envelope 中明确返回一个空 JSONPatch：仍为 `nochange`，并明确标记 `semanticProof:false`。
- 非空修复经官方 MVU 产生变化且同楼读回一致：`applied`。
- 非空修复经官方 MVU 解析后零变化：`unverified` / `complete_with_warning`，保留手动复检入口；不猜测它究竟是已经满足还是被官方执行器忽略。
- 诊断期间触发输入或上一助手 MVU 快照变化：走已有 `STALE_TASK`，不把旧证据的补丁写到当前楼。
- 人物阶段失败或页面刷新后：从同一正文、同一 generation key 的小型收据恢复变量结果；警告仍是警告。
- 人物与 World 的独立阶段不会因为该警告被删除或伪装成变量已证明正确。

## 本候选的恢复与报告改动

本次候选还修改了既有 Doctor 的恢复、取消和报告路径，并非只修改提示词。Story Oracle 的提示、请求、区块提取与官方 MVU 执行链继续复用；World 的原生存档、推演与重 roll 继续独立运行。以下是上游没有 Doctor 跨模块身份信息而必须在适配层处理的部分：

- 诊断完成收据保存触发输入、前一 MVU 与当前楼 MVU 的摘要，并通过原生 World IndexedDB 存储保存；恢复人物阶段不会静默重放变量模型。
- 人物提交保存直接前态与分支前态；当前证据改变时恢复这一笔提交。缺失或损坏的前态不会被新模型返回覆盖。
- 已完成历史楼与正在提交的楼分别核对：正常发送下一轮后停止生成，不应撤销上一轮已经完成的档案。
- 手动 MVU 复检成功后继续本楼人物阶段，公开调用仍返回原变量诊断结果；面板记录完整流水线结果。
- 完整报告写入结束后才显示本轮完成；报告失败不撤销已经落地的变量和人物。已有完整性事故时不会再展示可以直接重试人物的入口。
- 旧证据的副作用已完整撤销时，恢复结果保留 `stale`，不把它重新标为一次普通模型失败。

这些适配未改变数据库的独立填表，也没有向私人预设之外写入用户提示内容。成熟来源核对使用 Story Oracle 固定快照、World Core 的当前态/存档点/楼层边界及 ver5.35 的原结果与单次格式修复；Doctor 收据、跨阶段补偿和统一报告属于新写的整合代码，不能冒充上游原样实现。

本版本用于单个真实宿主、按回合等待结算的连续功能试跑，尚未完成真实门禁。跨页面并发提交、已应用变量在异常中断后缺少可核验前态的恢复仍有未完成的审查项；遇到后一种情况会保留事故状态与导出入口，不能声称已经自动修复。用户本轮明确暂缓 120 秒停止门槛，试跑只记录耗时；即使连续十二轮通过，也不能由此声称正式性能门禁完成。
