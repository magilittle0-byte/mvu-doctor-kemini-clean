# 0.8.0 成熟原件移植与最小适配映射

## 重建边界

0.8.0 不继承旧 Doctor 的任务编排、提示词、人物 Schema、世界 Schema、解析器、状态机或“测试通过”结论。重建前的 0.7.5 仅以字节快照保存在 `legacy/0.7.5/`，根运行入口没有对它的 import、script 标签或动态调用。

本版的执行合同只有一条：一条最终回复在 `GENERATION_ENDED` 后必须经过不少于 500ms 的两次新鲜读取，并保持聊天、消息、swipe和正文指纹不变，才按 `变量诊断/修复 → 人物档案 → 世界推进` 串行执行。任一阶段失败时停止后续阶段并留下可单独重试的原始结果，不用空结果伪造成功。

## 最小适配

### Story Oracle 目标钉住

Story Oracle 原件的自动诊断以最新消息为目标。适配层关闭其原生自动调度，通过原件暴露的运行函数执行同一诊断链，但把 MVU 读写目标固定为已经接受的数值消息ID；每个异步边界重新核对 `chatId + messageId + swipeId + contentFingerprint`。这是避免重 roll、换聊天或新回复到来后误写“latest”的宿主适配，未改原件文件和诊断语义。

显式 `<JSONPatch>[]</JSONPatch>` 只表示模型没有提出修复，界面不会把它表述成“脚本证明变量正确”；无论空数组是独立返回还是位于正常 `<UpdateVariable>` 内，都沿用 Story Oracle 的 `nochange` 语义。缺少 `UpdateVariable` 且也没有显式空补丁则属于不可解析失败，保留原始返回供手动复检。

固定楼层的MVU基线必须真实存在；非空补丁必须产生实际变化，并在写入后从同一数值消息ID完整读回。手动复检若由Story Oracle在同一楼同一swipe补写变量块，适配层只在这次受控写回内把新正文身份迁移到原`generationKey`；外部任意编辑不能继承该身份。因此同一接受回合仍命中原世界收据，不会因为Doctor自己改了正文而再推进一次。

### 人物档案事务

ver5.35 没有 Kemini 人物档案字段，因此字段提示与聊天 metadata 存储必须由适配层提供。模型获得最终正文、玩家本轮输入、角色卡、活动世界书、修复后的 MVU、完整既有档案和候选人名；正文未说明的资料应在不冲突的前提下主动补齐，并标记为以后可修订的推断。

输出经 ver5.35 的宽容解析方式处理。人物发现结果与档案必须双向对应；存在高置信候选时空数组不能通过。整批解析和最低可用性检查成功后才一次写入 metadata，失败时不留下半张档案。每个消息/swipe保存独立分支，重 roll 恢复该分支基线，不把旧 swipe 档案注入新 swipe。

已存人物的明确姓名命中、明确句首发言者、句界后紧邻动作词的二至四字短主语和稳定NPC编号形成高置信必覆盖候选；角色卡名、标题式对白、泛化称谓、玩家代词开头片段、以助动词结尾的片段以及更长的自然语言动作主语都交给模型结合正文判断，不能被脚本正则升级成虚假必建档人物。首次空档案无论有无候选都必须经过那一次定向复核，避免模型用一次偷懒空数组跳过本轮新人。

### World Engine 私密上下文与手动轮次

World Engine 原件继续拥有世界状态和推演。适配层把其模式设为 `manual`，避免和 Story/人物阶段并发；在原件 `buildPromptSection` 的返回值后追加完整人物档案、修复后的当前 MVU 和一份全局模型附加提示词。追加文本明确：后台秘密不是玩家知识；人物、势力、环境与社会过程依自身目标、有限知识、资源和阻力行动；尝试不等于成功；正文镜头外事件应留在后台。

正文注入不把完整世界对象直接交给叙事模型。适配层先深拷贝原件状态，再把副本中的 `blackbox.secretActions` 与 `blackbox.secretAssets` 清空，随后才调用原件 `buildContext`；World Engine 私有状态本身保持原样。这一最小外层投影直接复用本仓 `WORLD_ENGINE_V5_ANTI_OMNISCIENCE.md` 的“后台真相与正文输入分离”边界，不修改冻结 vendor。

普通接受回合只调用一次 `manualEvolve('forward')`，成功必须使世界轮次恰好增加一次；重 roll 按原件自动重 roll 的调用语义省略 mode，并要求轮次保持不变。`redo` 只属于原件的手动检查点重做，不用于聊天重 roll。

## 必须新写的宿主胶水

没有一个参考作品同时负责“Story Oracle修MVU、ver5.35式人物填表、World Engine后台推演”三者的酒馆顺序，因此以下内容没有可直接移植的同等原件，只写在 `index.js`、`profile-engine.js` 和 `style.css`：

- 三套原件装载与就绪检查；
- 接受正文的新鲜读取和精确消息/swipe指纹；
- 单一串行主链、阶段取消和失败单步重试；
- `GENERATION_STARTED/ENDED`生成票据、流水线检查点和世界提交收据的分层恢复；
- 用户显式取消墓碑，以及手动变量修复成功后从人物阶段继续的接力；
- 人物档案的聊天隔离、分支、原子 metadata 提交和刷新读回入口；
- 一个 API 表单和一个全局自定义模型附加提示词入口；
- 除 API 地址、模型、密钥和授权头以外的完整运行报告；
- 桌面有界、手机动态视口全屏的统一控制台。

这些胶水不得重新审判 Story Oracle 已完成的变量语义，也不得建立另一份 World Engine 世界真相。

生成票据只保存聊天ID、生成序号、类型、预期楼层/swipe、基线身份和随机`generationKey`，不保存正文或API。`normal` 生成必须在票据基线之后真实出现本轮用户楼才可接管；没有用户楼的数据库/扩展后台生成即使同样报告为 `normal` 也会被丢弃，不能覆盖主正文票据、取消人物提交或推进世界。`MESSAGE_SENT` 早于或晚于 `GENERATION_STARTED` 的两种 Tauri 顺序都归入同一票据。流水线接管前先持久化`running`检查点再删除短票据；刷新时旧内存计时器会失效，持久票据重签为唯一新所有者，避免漏跑或双跑。用户取消把精确检查点改为`cancelled`，恢复器不会把它当作中断任务复活。

## 所有权没有合并

- 预设：只负责正文生成前的篇幅、文风、视角、人物首次出场和玩家边界；私有预设不进入仓库。
- MVU：拥有实时变量；Story Oracle只对本楼错误进行诊断/修复。
- 数据库：数据库本体独立填自己的表，Doctor不读取其成功状态冒充人物档案提交。
- Doctor人物档案：存于当前聊天 metadata，只供人物连续性与世界后台使用。
- World Engine：拥有私密世界、主体、势力、环境、事件与推进轮次。

## 当前证据边界

仓库检查可以证明：三套冻结原件哈希一致、脚本可解析、离线主链顺序和空档案门成立、响应式 CSS 合同存在。它不能证明目标模型服从提示、真实 MVU 写入正确、TauriTavern 持久化读回、世界每轮有效推进或十二轮性能达标。

任一运行文件或提示词改变后，旧真实证据立即失效。只有当前源码指纹在真实 TauriTavern/SillyTavern、当前模型、当前角色卡、当前预设、内嵌世界书、数据库、缝合怪与MVU同时启用环境下完成唯一十二回合流程，才可从“测试候选”升级为“已真实验收”。
