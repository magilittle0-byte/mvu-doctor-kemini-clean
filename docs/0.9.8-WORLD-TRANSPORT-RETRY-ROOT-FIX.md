# 0.9.8 World 运输错误兼容根修

## 真实失败

0.9.7 在全新聊天首轮完成正文与 Doctor 后，原生 World 的提示和人物附加段均只进入请求一次，但代理把运输错误包装成 HTTP 成功响应里的 `choices[].message.content`。原生 World 将这段非 JSON 文本交给宽容解析器，解析失败后按设计回滚：`evolve()` 返回 `false`、`round` 保持 0、`lastEvolveResult` 不存在，只保留本地骰出的 pending 重试票据。因此该回合不计入连续试跑。

## 成熟来源与最小适配

| 能力 | 成熟来源 | 0.9.8 采用方式 |
|---|---|---|
| World 提示、独立 API、宽容 JSON、合并、骰子、回滚、存档、轮次、下一轮注入 | DlSNlGHT World 3.0.2 原件 | 原样保留；本次不修改 vendor |
| 显式运输错误信封识别 | 已内置 Story Oracle 1.35.4 的 Doctor 适配 | 复用同一组窄正则，只识别 `[API 错误]` 等明确错误信封或带 4xx/5xx 的请求错误 |
| 同请求恢复 | Story Oracle Doctor 的运输错误内容恢复 | 在现有 `WORLD_ENGINE_API.callApi` FIFO 适配层内，以相同参数和 signal 最多重试一次 |

没有新增调度器、解析器、世界 schema、业务门禁或模型调用阶段。第一次返回普通内容时仍只有一次网络调用；只有位于整条返回开头的明确错误信封或短状态回执才有第二拍，合法 JSON 字段内叙述 HTTP 错误不触发。第二拍仍为同类错误时抛出 `world_api_transport_error_content`，不保存或传播原始响应，也不把它冒充 JSON 格式问题。既有 FIFO 标记增加 `version` 与 `installed` 收据：同版本保持幂等，旧版本同页升级时从已保存的原始 World API 重新安装当前包装器，而不是继续使用旧逻辑或叠两层。

## 所有权

- 预设仍只负责正文生成前约束。
- MVU 仍由官方 `Mvu.parseMessage` 和固定楼层写回负责。
- 人物档案仍由 Doctor 在正文后补全并原子提交。
- World 的状态推进、解析、合并、回滚、持久化和注入仍由 World 3.0.2 原件负责。
- 数据库未被 Doctor 或 World 接管。

## 验证边界

受控回归覆盖：合法响应一次通过；合法 JSON 内含 HTTP 错误叙述仍只调用一次；明确运输错误后同参数第二拍成功；连续两次错误信封类型化失败；普通非 JSON 文本不被误判为运输故障；0.9.7 无版本收据可原地升级；FIFO、失败释放和取消语义保持。真实运行代码已改变，0.9.7 的失败现场只用于根因取证，不能作为 0.9.8 的成功证据；必须在全新聊天从第 1 回合重新开始连续真实试跑。
