# 0.9.0 原生 World 所有权恢复与最小适配来源映射

## 1. 结论

0.9.0 不再由 Doctor 复制一条“世界阶段”来调用 World Engine。世界推演从触发、读取上下文、调用模型、解析、重试、合并、存档、重 roll、注入到界面，全部交还给仓库内置的原生 World Engine 3.0.2。

Doctor 只保留六个与宿主整合有关、且上游原件无法替项目完成的最小适配：

1. 以独立 World/Memory 迁移键恢复 0.8.x 精确旧签名，Memory 可保持 `pending` 跨启动重试；
2. 把原生 `evolveFilterRegex` 的两类 Story Oracle `UpdateVariable` 完整外层块清理维持为严格启动合同，并在快照外为原生 `filterDialogue` 与直接 `evolve` API 建立同规则的运行期防线；
3. 新聊天第一次使用且尚无选择记录时，以每聊天单 Promise 预热，并在首次 `evolve` 未就绪时执行第二次 single-flight 重试；
4. 包装原生 `WORLD_ENGINE_EVOLUTION.evolve`，只等待同楼变量诊断进入成功或失败终态；并发手动复检用带单调 token 的 `manualDiagnosisBinding` 防止旧终态提前放行及旧任务误清新绑定；
5. 在传给原生 `buildContext` 和 `MEMORY_ENGINE.ingestWorldEvolution` 的副本中建立可观察投影，防止秘密经正文或记忆联动回流；
6. 只读展示原生 World 状态、诊断和注入快照，并提供打开原版完整面板的入口。

变量复检和人物档案仍由 Doctor 负责。World 只等待变量诊断“已经结束”，不要求诊断成功；人物补档的成功、失败、取消、恢复或重试都不是 World 的前置条件。World 也不再成为 Doctor 人物提交的后置步骤。

## 3. 原样复用的原生运行链

以下能力全部由 `vendor/world-engine-v3.0.2/` 原样提供，0.9.0 不再写第二套实现。

| 世界状态、稳定 ID、checkpoint、fingerprint | `world-engine-core.js` | 原样读写；Doctor 不再保存或恢复第二份世界检查点 |
| 世界提示、因果顺序、公开传播、黑盒、模型调用、宽容解析、自动重试、状态合并 | `world-engine-evolution.js` | 原样运行；Doctor 不新增世界提示或解析门禁 |

| 世界书读取与显式选择记录 | `world-engine-worldbook.js` | 原样读取；Doctor 只在从未保存选择的新聊天做一次初始化 |
| 当前状态或 checkpoint 的轮次判定与正文注入 | `world-engine-inject.js`、`world-engine.js` | 原生注入；Doctor 只在传入原生 `buildContext` 的副本上做可观察投影 |

| 状态面板、设置、手动推进、重填、导入导出与编辑 | `world-engine-ui.js`、`style.css` | 原版完整面板继续是 World 的控制面；Doctor 只提供跳转入口 |
| 聊天隔离、缓存、存档同步与锚点保护 | `world-engine-store.js`、`world-engine-chatcache.js` | 原样运行；Doctor 不另造 world receipt |
| 原生 Memory Engine 的提取、时间线、回滚和有界注入 | `memory-engine*.js` | 保持启用和独立；Doctor 只投影 World→Memory 的公开输入，原生 `replace` 回滚、空摘要跳过与持久化不被替换 |

原生控制流可概括为：

```text
宿主生成结束事件
  -> World 自己判断 auto / time / manual 与新轮次 / 重 roll / redo
  -> 适配屏障等待：本聊天世界书首次选择 Promise + 同楼变量诊断终态
  -> 原生 filterDialogue 前后清理机制块，期间仍执行用户其余过滤规则
  -> 原生 evolve 读取已清理机制块的最近对话、世界书、Memory、世界状态与 tonePrompt
  -> World 自己调用模型、宽容解析并按设置重试
  -> World 自己合并状态并维护 checkpoint / fingerprint
  -> World 自己刷新注入、诊断与原版 UI
  -> 启用原生 Memory 联动时，只把公开投影交给原生 ingestWorldEvolution
```

屏障没有创建新的世界 scheduler，也没有改变 forward、redo 或重 roll 的分支选择；这些决定在进入屏障前已经由原生 World 完成。屏障只等待 Doctor 的 `diagnosis` 终态，不等待 `profile`，诊断失败或屏障自身异常都不会把原生 World 永久关死。

## 4. 从 0.8.x 删除的重复接管

| 已删除机制 | 旧问题 | 0.9.0 所有权 |

| Doctor 串行执行 `diagnosis -> profile -> world` | 变量或人物失败会让世界完全不推进 | Doctor 只执行 `diagnosis -> profile`；原生 World 仅等待 diagnosis 终态，不消费 profile 或 world 阶段 |
| Doctor 主动调用 `manualEvolve` 作为每回合世界调度 | 绕过上游对新轮次、重 roll、redo 和时间模式的判定 | 原生 `world-engine.js` 调度 |
| `world receipt`、世界阶段 checkpoint 与 forward 恢复 | 与原生 checkpoint/fingerprint 产生双重状态和错误恢复语义 | 原生 Core、Store 与 Chat Cache |
| 把 continue 当作重 roll 的额外分支 | 破坏上游已经区分的 forward / redo / swipe 语义 | 原生重 roll 与楼层判定 |
| Doctor 取消时调用 World abort | 用户只想取消变量/人物任务时会误杀独立世界推演 | Doctor 取消只作用于 Doctor |
| 全人物档案、整份 MVU、全局提示和世界书的永久上下文 monkeypatch | 重复、超量且改变上游提示数据所有权 | 原生 World 上下文组装 |
| 强制关闭 Memory Engine 或覆盖其设置 | 丢失上游原生有界记忆能力 | 原生 Memory Engine 设置 |
| Doctor 世界页复制设置、重试和推进按钮 | 两个控制面会互相覆盖且状态不同步 | 原版 World UI 为唯一完整控制面 |

旧聊天中已经持久化的 Doctor 世界收据不再驱动任何世界执行。若旧 Doctor checkpoint 停在 `nextStep: "world"`，只把该 Doctor 任务迁移为已结束；不会据此调用、回滚或改写原生 World。

## 5. 最小适配

### 5.1 可恢复的旧设置精确迁移

来源：`index.js` 的 `migrateWorldSettings`。

- World 与 Memory 使用独立状态键：`mvu_doctor_native_world_owner_v1` 和 `mvu_doctor_native_memory_owner_v1`；
- 只把 `evolveMode: "manual"`、`engineEnabled: true`、`injectIntoPrompt: true`、`syncToChat: true`、`autoBackup: true` 同时命中的精确五字段组合认定为 0.8.x 强制写入签名；
- 仅对这份精确签名恢复 `evolveMode: "auto"`、`syncToChat: false`、`autoBackup: false`；任一字段不同都按用户拥有的 World 设置保留；
- 在改变 World 五字段前，先把独立 Memory 键写成 `pending`，把“这确实来自 0.8.x 强制写入”的来源证明持久化；World 键随后可以独立完成；
- Memory 键为 `pending` 时，即使 World 已经不再呈现旧五字段签名，后续启动仍会继续尝试 Memory 迁移；Memory 接口暂不可用、写入失败或写后无法读回都保留 `pending`，不会被 World 的 `done` 吞掉；
- Memory 精确为 `engineEnabled: false`、`evolveMode: "manual"` 时，恢复为上游 `engineEnabled: true`、`evolveMode: "auto"`，并且只有成功读回这两个目标值才写 `done`；
- 若读取后确认 Memory 已不是精确 `false/manual`，视为用户设置或已经恢复，只写 `done` 而不改值；其他 Memory 字段始终保持原值；
- 仅在 World 自己缺少 API 配置时迁移旧共享连接字段；
- 不持续覆写 `engineEnabled`、注入开关、节拍或 Memory 设置；
- 两个迁移键都进入 `done` 后，后续设置完全由原生 World/Memory 保存和拥有。

这是兼容旧安装所必需的新胶水，不能从上游直接复制，因为上游不知道 Doctor 0.8.x 写过哪些遗留字段。独立 `pending` 不是长期接管；它只防止初始化时序让原本可恢复的 Memory 被永久遗留在关闭/手动状态。

### 5.2 原生对话过滤器的 MVU 完整 payload 合同

来源：`index.js` 的 `MVU_DIALOGUE_FILTERS`、`filterMvuMechanismBlocks`、`migrateWorldSettings`、`installWorldDialogueFilterBridge` 与 `installWorldEvolutionDiagnosisBarrier`。持久执行点仍是原生 World 的 `filterDialogue` / `evolveFilterRegex`，运行期保护位于 vendor 快照之外。

适配合同包含两条正则：

- 清理完整的 `<UpdateVariable>...</UpdateVariable>`；
- 清理从 `<UpdateVariable>` 开始但因模型截断而没有闭合标签的尾部。

每次启动都会使用原生 `WORLD_ENGINE_CORE.filterDialogue` 分别验证闭合块与截断块样例。探针不只在 JSONPatch 内放唯一 payload，也在 `<UpdateVariable>` 外层、JSONPatch 之外放另一份 payload，然后严格比较完整过滤结果：

- 闭合块的结果必须精确等于 `前文后文`；
- 截断块的结果必须精确等于 `前文`。

因此只删除 `<UpdateVariable>` 标签名、只删除嵌套 JSONPatch、只让某个哨兵消失，或残留任何外层分析文本，都不满足合同；这些残留仍会污染 World 的因果输入。

持久规则先按行拆分并移除两条项目规则的所有精确重复项，用户其余规则及相对顺序保持不变。然后只用这份用户规则运行上述两个完整探针：

- 两项都精确通过：说明用户已有等价的完整块清理，最终只保留用户规则，不重复项目规则；
- 任一项不精确：同时把项目的闭合规则、截断规则按该固定顺序放在最前，再接回全部用户规则。

两条必须共同前置而不是逐条追加：闭合规则先完整删除有结束标签的块，截断规则再兜底真正未闭合的尾部；若宽泛的用户规则先只删标签，后续规则就失去外层定界并留下 payload。每次启动先去掉项目规则的精确重复项，也保证设置不会因反复迁移而膨胀。这样做不改变可见正文，不解析变量语义，也不把 Doctor 的 MVU 状态桥接进 World。

迁移完成后，boot 调用 `installWorldDialogueFilterBridge`，在 vendor 快照之外包装原生 `WORLD_ENGINE_CORE.filterDialogue`：

1. 入参先经过 `filterMvuMechanismBlocks`，用同两条 Story 成熟规则无条件删除闭合或截断的完整外层块；
2. 把清理后的文本与原 `settings` 交给原始 `filterDialogue`，因此用户配置的其他过滤规则仍由原函数按原语义执行；
3. 原函数返回值再次经过 `filterMvuMechanismBlocks`，避免其他过滤的组合结果重新留下完整或截断机制块；
4. 原生普通自动推进、手动推进和批量回填只要调用 Core 对话过滤器，都会共享这条运行期保护。

因此用户即使在同一次会话里通过原版 UI 删除持久 `evolveFilterRegex`，已经安装的 Core 包装仍能保护上述三类原生路径；它不把规则写回持久设置，不修改 vendor 文件，也不改变 scheduler、自动/手动模式、重 roll 或调用顺序。

`WORLD_ENGINE_EVOLUTION.evolve` 入口还有一层直接 API 防线。包装在等待诊断与调用原函数前，用相同两条规则分别生成 `safeAiMsg` 和只替换 `dialogueText` 的 `safeOpts`，让 `waitForWorldDiagnosis` 与原始 `evolve` 都接收安全副本。这一层覆盖可能绕开 `WORLD_ENGINE_CORE.filterDialogue` 而直接调用 `evolve` 的入口，不是普通/手动/批量回填之外的第二套调度；它也不修改调用者原对象或持久设置。

下一次启动仍会按上述严格外层结果合同检查并按需补回持久规则。Core 前后清理和 `evolve` 直连防线只建立输入安全边界，不绕过用户其他过滤，也不重建第二套世界配置。

### 5.3 新聊天世界书首次初始化与原生 evolve 等待

来源：`index.js` 的 `initializeWorldbookSelectionOnce`、`ensureWorldbookSelectionForCurrentChat` 与 `installWorldbookSelectionInitializer`；复用 `WORLD_ENGINE_WORLDBOOK` 的公开 API。

初始化遵守上游 `hasSelection` 的语义：

1. 已经存在选择记录时不改动，包括用户明确保存的空数组；
2. 读取当前世界书条目后再次核对 chatId，避免异步期间切换聊天造成串档；
3. 读取结束后再次确认仍无选择记录，避免覆盖同时产生的用户选择；
4. 没有条目时不写空记录；
5. 只把当前未禁用条目的 ID 交给原生 `saveSelectedIds(..., "world")`。

同一 chatId 的每次初始化尝试由单个 Promise 共享，避免聊天加载与 World 同时创建重复选择：

1. `CHAT_LOADED` 先触发最多两次重试的预热，并发布 `ready` 或 `pending`；
2. 原生 `evolve` 屏障先 `await` 当前 single-flight；
3. 若预热在内嵌世界书真正可读取前已经以 `false` 结束，且当前仍没有显式选择，屏障会清掉该已完成 Promise；
4. 屏障随后创建第二个、仍按同 chatId single-flight 的最多三次重试，而不是把预热的 `false` 当成永久结论；
5. 切换聊天会建立新的 Promise 作用域，旧聊天异步结果不能写进新聊天。

桥接状态通过 `MVUDoctorWorldbookBridgeStatus` 发布：预热中或等待首次推演重试为 `pending`，成功为 `ready`，首次推演仍未读到选择为 `missing`，初始化抛错为 `error`。Doctor 的 World 页显示当前状态和普通语言说明，完整报告保存导出时同一份 `worldbookBridge` 证据。`missing/error` 时原生 World 按自己的空选择语义继续并明确要求在诊断页核查，不伪造“世界书已加载”。

这是宿主体验适配：上游原版会在第一次打开原版面板时初始化选择，而 Doctor 用户未必先打开该面板。适配只提前执行相同的公开选择动作，不改世界书内容、触发规则或后续用户选择。

### 5.4 变量诊断终态屏障

来源：`index.js` 的 `installWorldEvolutionDiagnosisBarrier` 与 `profile-engine.js` 的 `waitForWorldDiagnosis`。

适配层包装的是 `WORLD_ENGINE_EVOLUTION.evolve`，不是宿主事件、scheduler 或 `WORLD_ENGINE.manualEvolve`：

1. 原生 scheduler 先完成模式、楼层、forward、redo 和重 roll 判定；
2. 进入原生 `evolve` 前，屏障按 chatId、楼层、swipe 和清理机制块后的正文指纹绑定同一最终回复；
3. 等待对应 Doctor checkpoint 离开 `nextStep: "diagnosis"`，或进入 complete、failed、stale、cancelled 等诊断终态；
4. 手动 MVU 复检开始前，以 chatId、楼层、swipe 和同一 generationKey 设置 `runtime.manualDiagnosisBinding`；即使磁盘上仍有旧的诊断终态 checkpoint，屏障也不会在这个手动绑定释放前误判为“本轮已完成”；
5. 每个手动绑定还取得递增的 `manualDiagnosisSerial` token；`finally` 只有在运行时当前 token 仍等于自己的 token 时才能清理，因此旧复检晚结束也不能删掉后来复检建立的新绑定；
6. 手动复检异常仍会通过自己的 `finally` 安全释放；绑定只保护同 scope、同 generationKey，不阻塞别的聊天或重 roll；
7. 诊断成功和诊断失败都继续调用原始 `evolve`；人物阶段不在等待条件内；
8. 若当前回复已经变为另一 swipe/楼层或 generationKey 切换则返回 stale，避免把旧回复推进到新分支；
9. 若屏障代码自身异常，记录警告并按已清理的正文调用原始 `evolve`，避免适配故障永久杀死成熟生命周期。

屏障解决的是顺序问题：World 不应在 Doctor 自动诊断或并发手动复检仍可能改写本楼 MVU 机制块时抢先读取同一回复。`manualDiagnosisBinding` 不是新世界任务或持久锁，只是防止已有旧终态证据造成早放行。屏障不评价诊断是否正确、不根据诊断结果决定世界是否允许推进，也不产生世界 receipt/checkpoint。

### 5.5 正文与 Memory 联动的可观察投影

来源：`profile-engine.js` 的 `projectObservableWorld`、`observableWorldDigest`、`installWorldMemoryPublicProjection` 与 `installWorldPublicProjection`。

上游世界推演必须看到完整后台状态，才能继续推进秘密行动、势力目标、仇敌追踪和因果传导；但原生注入器的完整上下文会让下一轮正文模型直接看到玩家视角尚不可知的后台信息。为满足本项目“世界后台知道、正文视角只知道可观察结果”的防全知边界，适配只在原生 `WORLD_ENGINE_INJECT.buildContext` 的入参副本上执行：

1. 深拷贝准备注入的 World state；
2. 隐藏 `worldDigest` 后台摘要；
3. 从 `events` 中移除尚未爆发或完成的后台事件，只保留已经爆发或完成的终局/公开事件；
4. 在 `factions` 中隐藏 `currentGoal`、`core_person` 与 `powerPillars`，不向正文暴露势力内部意图、关键人和力量支柱；
5. 隐藏整个 `enemies`、`influenceChain` 与 `blackbox`；
6. 保留原生公开风声，以及趋势、经济、声誉、区域事件等可观察层；
7. 把投影副本交回原生 `buildContext`；
8. 不修改原生持久状态、checkpoint、世界面板、诊断或下一轮世界推演输入。

同一投影也用于原生 World→Memory 联动，但不接管 Memory：

1. `installWorldMemoryPublicProjection` 在 vendor 快照之外包装 `MEMORY_ENGINE.ingestWorldEvolution`；
2. `payload.worldUpdate` 的副本先经过同一公开白名单；
3. 原始后台 `worldDigest` 不进入 Memory，改由公开事件、风声、趋势、势力外显状态、经济信号、声誉变化和区域事件按固定顺序生成确定性公开摘要；
4. 原 payload 的 `layer`、`worldRound`、`replace`、`force` 及其他原生控制字段通过展开保持原样；
5. 只有后台秘密而没有任何公开条目时，公开摘要为空。原生 Memory 仍会在 `replace: true` 时先回滚该楼旧 World 联动，再因 `empty_digest` 跳过新增纪要，因此重 roll 的替换语义不丢失，也不会制造“本轮无公开变化”的假纪要；
6. 实际回滚、跳过、生成、存储和时间线仍全部由原生 Memory 实现，完整 World 状态、`lastEvolveResult`、checkpoint 和后续推演输入不被修改。

`winds` 的 Memory 投影复用原生可见阈值：默认只保留 Lv3/4，只有用户明确设置 `injectAllLevels=true` 才纳入 Lv1/2，且 `worldUpdate` 与确定性公开摘要都在完成该阈值过滤后生成。

因此存在三条严格分开的数据视图：

```text
持久 World / 原生 evolve：完整后台状态
原生 buildContext -> 正文模型：可观察投影
原生 ingestWorldEvolution -> Memory：可观察更新 + 确定性公开摘要
```

秘密产生合法公开后果时，应由原生 World 先把后果写成公开风声、已经爆发或完成的事件，或趋势、经济、声誉、区域等其他可观察状态，再进入正文。只写入 `blackbox`、`enemies`、`influenceChain` 或势力内部字段仍属于后台，不会因为存在于面板数据里就被正文模型提前知道。

这是项目级的防全知边界，不是第二套注入器或记忆引擎。它不删除持久 World 信息，不改变世界提示、世界演化输入或状态所有权；只限制正文模型和原生 Memory 联动各自收到的副本。

### 5.6 只读状态、报告与入口

来源：`profile-engine.js`。

- Doctor 世界页从原生 `WORLD_ENGINE_CORE.loadState()` 读取轮次和状态；
- 同一页显示 `worldbookBridge` 的 `pending/ready/missing/error` 状态与说明，不用世界轮次掩盖世界书等待或缺失；
- 完整报告只读附带 `WORLD_ENGINE_DIAG.collect("world")` 与 `WORLD_ENGINE_INJECT_INSPECTOR.getLastSnapshot("world")`；
- 完整报告同时保存导出时的 `worldbookBridge`，便于离线区分“仍在等待”“原生 World 使用空选择”和“本轮已取得内嵌世界书选择”；
- “打开原版 World”调用原件 UI 的公开入口；
- Doctor 不提供自己的世界推进、世界失败重试或世界状态提交按钮；
- 连接页只有用户明确保存时才写入 World 的公开 API 字段和 `tonePrompt`，不会改写原生调度、同步、注入或 Memory 开关。

这里的新代码只解决统一控制台的可见性和入口问题；世界状态解释、编辑和恢复仍在原版完整面板内完成。

## 6. 独立失败语义

```text
同一条最终正文
  ├─ Doctor：变量复检 -> 人物补档/更新 -> Doctor 持久化与报告
  └─ World：原生事件/scheduler -> 等变量诊断终态 -> 原生 evolve -> 原生持久化/注入/UI
```

- 变量检查运行中：本楼原生 `evolve` 等待，避免从尚未确认的同楼内容抢跑；
- 同 generationKey 的手动复检运行中：`manualDiagnosisBinding` 继续持有等待，旧 checkpoint 即使已经终态也不能早放行；
- 变量检查失败：屏障把失败视为诊断终态并放行原生 `evolve`，不把“诊断失败”误写成“世界不得运行”；
- 世界书预热未就绪：首次 `evolve` 再做一轮 single-flight 重试；仍缺失或报错时记录可见状态后按原生空选择继续；
- 人物发现、生成、解析或提交失败：Doctor 保留自己的失败状态，不拦截 World；
- Doctor 被取消：只取消 Doctor 的任务，不调用 World abort；
- World 调用、解析或持久化失败：由 World 自己的重试、诊断和原版 UI 处理，不伪装成变量或人物失败；
- 一方成功不冒充另一方成功；Doctor 的 `world.status = "native-independent"` 表示状态与执行所有权独立，不表示时间上零等待，也不是一次世界推进成功收据。

## 7. 复用等级汇总

| 范围 | 复用等级 | 原因 |
|---|---|---|
| `vendor/world-engine-v3.0.2/` 全部 45 个上游文件 | 原样复用 | 上游已经完整解决世界调度、提示、解析、重试、状态、恢复、重 roll、注入和 UI |
| 原生 Worldbook、Core、Evolution、Diag、Inspector、UI 公开 API | 最小调用适配 | 只增加首次选择的两阶段 single-flight、Core `filterDialogue` 前后机制块清理、直接 `evolve` API 防线、诊断终态顺序、状态报告和控制台入口，不取得世界状态或 scheduler 所有权 |
| 旧 Doctor World/Memory 精确签名迁移 | 不得不新写 | 上游不知道 Doctor 0.8.x 的强制五字段、Memory `false/manual` 以及需要跨启动保留的独立 `pending` 来源证明 |
| `UpdateVariable` 完整外层块清理合同 | 不得不新写 | World 上游不知道 Story Oracle/MVU 的机制块；持久规则由原生过滤器执行，运行期 Core 包装在原函数前后清理并保留用户其余过滤，直接 `evolve` 参数副本再覆盖绕开 Core 的调用 |
| 变量诊断终态屏障与手动绑定 | 不得不新写 | 同时安装 Doctor 与 World 时需要建立同楼读取顺序；上游不知道 Doctor 的诊断 checkpoint 或并发 `manualDiagnosisBinding` |
| 正文与 Memory 联动的可观察投影 | 不得不新写 | 本项目要求完整后台继续推进，但正文模型和后续记忆注入都只能读取合法公开或可观察结果，同时必须保留原生 `replace` 回滚语义 |
| Doctor 变量复检与人物档案 | 既有独立模块 | World 上游不负责 MVU 修复和本项目人物档案；它们不得反向接管 World |

0.9.0 没有新写世界提示词、世界 JSON Schema、世界解析器、世界合并器、世界重试器、世界 scheduler、世界 receipt 或世界 UI 替代品。`evolve` 包装只建立前置等待，最终仍调用上游原函数。
