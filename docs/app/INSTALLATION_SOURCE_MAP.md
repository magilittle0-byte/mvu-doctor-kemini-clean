# 统一安装与前端接入来源（2026-09-28）

本轮只恢复用户前端和一次安装启动三模块；用户所说省 token 指 Codex 工作额度，不修改医生模型、提示词、正常请求数、推演、保存或修复语义。新组合是待真实验收候选，旧锁与旧验收文件保持原字节，不能证明本候选通过。

1. 故障路径：根 manifest 只启动 P1，P2/P3 依赖额外导入；旧悬浮入口没有接入。根 manifest 又被 P1 的历史验收锁覆盖，换入口即导致 P2/P3 拒绝启动。真实宿主三面板都在关闭的扩展设置中。
2. 来源：旧 `index.js`（0.9.11）的 `boot`、`waitFor`、`assertStoryContract`、`assertWorldContract` 以实际组件就绪和兼容版本启动；旧 `profile-engine.js` 的 `ensureUi` 和 `style.css` 提供统一壳；当前 `profiles/entry.js`、`world/entry.js` 的 owner 集合、pending 和 dispose 提供单实例与卸载。相关上下游为当前三个 runtime.bind 与 install/loader 文件。本次重新检索参考归档的数据库模板、Story Oracle、World、NPC Tracker、糖糖/Izumi/缝合怪资料；这些没有当前三模块的统一安装入口，不能直接替换现有数据写入者。
3. 原样保留：三个生成 runtime、模型连接、prompt、数据解析/持久化/修复和召回；旧锁及证据；现有 owner/pending/dispose 机制与各模块 UI 操作。旧版前端样式由新壳直接引用。
4. 最小适配：根 manifest 指向 app/entry.js；新入口顺序加载原 P1、以同一个存活 owner 启动 P2/P3并挂统一壳。P2/P3 启动检查改为模块清单声明的实际版本与 ready；历史验收 locked 仅代表对应原字节的验收，不能作为新候选的启动许可。新候选完整文件指纹由 check-app 及真实宿主读回验证，完整真实门禁仍必须执行。
5. 必须新写：三个现有入口的组合胶水和简短版本兼容检查，因为旧 0.9 引擎使用不同全局对象和存储，直接重启旧 profile-engine 会带回重复后台。统一候选文件校验覆盖根入口、壳、样式和三个模块，不能伪造旧锁或只校验后台。没有新增模型请求、并行状态机或修复器。

验收边界：本地语法/浏览器检查只验证接入机制；候选必须完整安装、在新聊天执行既定十二普通回合和压力覆盖，核对 UI、模块结果、修复与刷新。UI 查看和切换必须零生成调用。旧 1.x/2.0/0.9 后台不启动。
