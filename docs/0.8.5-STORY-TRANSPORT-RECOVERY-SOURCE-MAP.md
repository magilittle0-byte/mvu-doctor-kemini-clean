# 0.8.5 Story Oracle 运输错误恢复来源映射

## 真实失败

0.8.4 的真实 TauriTavern 首回合中，最终正文、固定楼层、swipe、MVU 基线和生成票据均稳定，但 Story Oracle 的直连后端转发返回了 71 字符的本地化 API 错误信封，正文明确包含 HTTP 520 状态。它被上游当作普通 `content` 返回，不含 `<UpdateVariable>` 或明确的空 `<JSONPatch>[]</JSONPatch>`。

Doctor 的 fail-closed 门禁正确停止了人物与世界阶段；原版 Story Oracle 则会把任何“没有提取到补丁”的内容直接归为 `nochange`，会把这类运输错误冒充成变量正确。

## 直接复用的成熟边界

- `vendor/story-oracle-v1.35.4/index.js` 的 `runAutoDiagnose()`、`callDirect()`、`callProfile()`、`extractUpdateBlock()`、`Mvu.parseMessage()` 与固定输出合同仍为主实现；冻结 vendor 未修改。
- Story Oracle 的 `callBackendForward()` 仍负责构造后端转发请求；适配层不复制端点、密钥、模型或请求协议。
- World Engine v3.0.2 的有界 `API fault → 原请求自动重试` 语义被最小移植到 Doctor 的 Story 阶段：只对已经证明为运输错误信封的返回重试一次，不新增路线状态机。
- ver5.35/当前人物填表事务的“原结果先校验，失败后只做一次定向恢复”提供相同的有界恢复边界；这里不降低诊断输出合同。

## 最小适配

`profile-engine.js` 只新增以下胶水：

1. 识别英文或本地化的明确错误信封，以及包含 HTTP 4xx/5xx 状态的请求失败回执；不依赖某一种标签语言；
2. 使用完全相同的 Story Oracle 请求自动重试一次，并在重试前复核任务所有权和固定楼层 MVU 基线；
3. 第二次仍为错误信封时，以 `story_oracle_transport_error_response` 失败，不进入人物或世界阶段；
4. 普通自然语言、无格式回答或其它无法识别文本仍走原有 `story_oracle_unrecognized_diagnosis`，不会被当成 `nochange`；
5. 完整报告保存每次诊断回执、恢复类别和最终错误码，仍不保存 API 密钥。

没有修改 vendor、没有增加新的持久任务类型、没有放宽空补丁证明、没有让脚本猜测变量是否正确。

## 回归要求

- 第一次本地化 API/HTTP 错误回执、第二次合法空补丁：只重试一次，然后按 `nochange` 继续人物与世界。
- 连续两次 API/HTTP 错误回执：明确失败于 diagnosis，人物和世界零调用，报告含运输错误码与两次回执。
- 普通无格式文本：仍立即失败，不走运输恢复。
- vendor 三套冻结校验必须逐字通过。
- 自动检查不等于真实酒馆验收；任一运行代码变化后，必须从全新聊天重新执行当前源码指纹的真实连续验收。
