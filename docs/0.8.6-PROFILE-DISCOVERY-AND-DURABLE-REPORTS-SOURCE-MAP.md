# 0.8.6 人物发现、恢复收据与报告真实落盘来源映射

## 真实失败证据

- 0.8.5 当前源码在真实 TauriTavern 第一回合完成了变量、完整人物档案、世界语义推进与一次性注入，但 Doctor 总耗时约 184.6 秒；第二回合再次超过 120 秒后按真实酒馆硬协议停止。
- 第一回合人物步骤先返回空档案并被强制复核，实际调用模型两次。旧提示把整份人物库、世界书、MVU 和重复正文同时发送，人物请求约 10.8 万字符。
- 同一页面的旧聊天与新聊天共用 `sessionStorage` 配额。现场约 5.20M 字符时，第六条完整报告无法保存；失败条目只留在内存，刷新会丢失。
- 独立审查进一步确认：仅凭“结构化候选为空”不能证明正文无人；`WORLD_ENGINE_STORE` 的同步镜像读回也不能证明 IndexedDB 的异步事务已经完成。

## 直接移植

### 结构化人物发现

- 来源：正式历史实现 `mvu-auto-doctor-v1.8-hotfix/index.js` 的 `actorNamesFromMvuData`。
- 来源：正式历史实现 `mvu-auto-doctor-v1.8-hotfix/actor-ledger-core.mjs` 的 `ACTOR_JSON_PATCH_CONTAINERS`、`taggedTextBlocks`、JSON Pointer 解码与 `jsonPatchActorFacts`。
- 来源：同一 Actor Ledger 的 `structuredContentActorFacts`。
- 当前落点：`profile-engine.js` 的 `actorNamesFromMvuData`、`ACTOR_JSON_PATCH_CONTAINERS`、`taggedTextBlocks`、`decodeJsonPointerSegment`、`jsonPatchActorNames` 与 `structuredContentActorNames`。
- 复用等级：发现骨架和基础解析代码直接移植；Actor fact 对象收窄为本适配器现有的姓名数组，并沿用玩家/机制标签排除器。当前实现另做了明确的定向扩展：支持 `小队/队伍 → 成员/队员` 嵌套、JSONPatch 数组下标及 `operation.value` 取名，以及结构标签的 `label/title/actor-id/id` 回退；这些扩展不冒充原件逐行代码。

### ver5.35 宽容解析与单次定向修复模式

- 来源：用户提供的角色生理状态引擎 ver5.35 原件。
- 当前落点：`profile-engine.js` 的 `stripCodeFence` → 标点归一化 → 平衡 JSON 提取 → 尾逗号修复链，以及每份模型结果“先验证原结果，失败后最多做一次定向修复”的控制模式。
- 复用等级：宽容 JSON 解析链逐行移植，输出标签从 `<life_state>` 最小适配为 `<人物档案>`；单次定向修复复用原件的处理模式。人物提示、字段结构、人物发现、分批验证和原子提交属于 Doctor 自己的适配实现，运行时不加载或调用完整的 ver5.35 生理状态引擎，因此不称为“ver5.35 填表链”或“ver5.35 填表事务”。

### 大容量报告存储

- 来源：冻结原件 `vendor/world-engine-v3.0.2/world-engine-store.js` 的 IndexedDB 数据库 `world_engine`、对象仓 `kv`、同步镜像和键空间。
- 当前落点：`doctorPersistenceStore` 继续使用原件公开同步接口；Doctor 的 durable adapter 写入同一个数据库和对象仓，不创建第二套数据库。
- 复用等级：数据库、对象仓、键空间与镜像接口直接复用；事务完成回执是原件公开接口缺失、但 Doctor 完整报告必须具备的宿主适配。

## 最小适配

- Story Oracle 1.35.4 由当前主链直接复用原件的世界书/MVU上下文构建、诊断提示、模型运输、更新块提取、正文写回与状态栏刷新组件；Doctor 另加固定消息楼层、任务所有权、运输错误恢复、显式空补丁、写后读回和失败回滚。当前运行的是“复用原版诊断组件的固定楼层适配链”，不是原件 `runAutoDiagnose/autoApplyFix` 整函数原样执行。
- JSONPatch 的 `/当前敌人/名称` 与 `/当前敌人/0/姓名` 读取操作 `value`，不把“名称”或“0”误建成人物。
- 实际 MVU 的 `小队/队伍 → 成员/队员` 嵌套结构加入现有递归发现器；结构化标签补齐成熟实现的 `display-name`、`actor-id` 与 `id` 回退。
- 结构化候选只负责“必覆盖人物”，不再承担“证明正文无人”。每个新最终正文至少由填表模型阅读一次；脚本没有结构化人名时，模型必须自行发现所有非玩家新人。已有完整档案只以姓名/别名注册表发送，不会因再次出现而被重写。
- 当前正文先由轻量名单请求发现全部新人，发现结果必须能在本楼正文或本楼结构证据中落地；完整档案再按当前输出上限的安全容量分批生成。初答、单次格式修复和返回别名都不能提前吞掉延后批次。当前新人不受 8 人维护预算截断；8 人预算只用于不在本轮的历史残缺档案。全部批次内存汇总，最后仍只做一次原子提交；任一批失败不落半张档案。
- 手动“重填本楼人物”与故障恢复分离：显式重填只重建本楼正文、JSONPatch 或人物标签指向的人物，不拖入整份 MVU 人物库存或其他楼层的历史残档；恢复/失败重试只处理残缺人物，软标题永不升级成强制人物。
- 人物档案与精确的 chat/message/swipe/fingerprint/profile digest 收据使用 World Engine 3.0.2 的同一 IndexedDB、对象仓和同步镜像，按显式 chatId 独立键原子提交；旧聊天 metadata 只作为一次性迁移来源，不再承担权威落盘。每次提交等待真实 readwrite 事务完成，再从 IndexedDB 只读事务核对整份字节；刷新落在“人物已提交、流水线尚未切到 world”的窗口时，恢复读取收据并以 0 次模型调用进入 world。
- 人物提示只投影待处理人物的完整旧档案，并复用旧 Doctor `cropForModel` 的首尾保留裁剪；最终正文不再在近期上下文中重复。
- 旧 `sessionStorage` 报告、清单和诊断会复制到成熟存储，原副本继续保留。Doctor 对 entry/index/manifest 使用同一 IndexedDB 事务并等待 `complete` 后再标记成功；同一聊天的报告读改写严格串行。目标报告损坏但旧副本有效时先隔离损坏内容，再恢复有效副本。
- CHAT_LOADED 先无持久化地取消旧任务并提升 epoch，再读取新聊天；每次加载还有独立序号，并绑定读取开始时的流水线 epoch。晚到的旧加载以及同一聊天里已被新生成取代的加载都不得覆盖或写入当前运行状态。损坏诊断不会被空数组覆盖；已发生且无法证明恢复的诊断缺页会持久锁定“不完整”，后续成功写入错误标记也不能洗绿。
- 重 Roll 沿用旧 Doctor 已验证的“独立 swipe 恢复世代 + 串行恢复链”边界，但只移植其任务所有权，不移植旧状态机：每次分支恢复都绑定独立 restore serial 与 chatId；取消只使旧令牌失权，不截断仍需完成或回滚的恢复尾链，新重 Roll和聊天加载必须等该尾链闭合。提交与回滚始终写同一个显式 chatId 的 IndexedDB 键，不依赖真实酒馆只会操作当前全局聊天的 `updateChatMetadata/saveMetadata`；回滚事务失败会升级为非 stale 红色故障并阻止后续流水线。生成期间正文暂时变化不会误杀仍然拥有该分支的恢复任务，旧 swipe 档案也不能进入新分支提示、存储、世界后台提示或后续公开注入。
- 导出先确认当前没有运行中的 Doctor 流水线，再排空报告与诊断写入，从当前聊天存储读取报告与 manifest，并逐项核对内存快照；异步 MVU 读取、下载和状态提示都复核 chatId/epoch/export owner/报告入队序号。运行中不会下载缺少最后阶段的“完整报告”；缺页时文件名和内容明确标为“不完整取证包”，也不污染后来切换到的聊天。

## 必须新写及原因

- `storeAfterProfileRun` 的人物提交收据：成熟 Actor Ledger 不拥有本项目简化的 swipe 分支格式，不能原样替换；收据与档案沿用成熟 World Engine 存储，而不是再创建 metadata 状态机。
- IndexedDB durable batch adapter：冻结 World Engine 同步接口是 fire-and-forget，没有事务完成/失败回执；Doctor 若直接把镜像读回算成功，会重现刷新丢报告。
- 设置草稿、报告完整性投影、惰性档案详情和 `visualViewport` 手机键盘适配：参考原件没有本项目这套控制台。手机布局使用真实可视高度与顶部偏移，不再人为保底到 240px，并同时跟随 resize/scroll。
- 浏览器夹具中的 Map 存储和结构化 MVU 样本只用于回归，不进入运行时代码。

## 明确未采用

- 没有并行人物与世界；冻结 World Engine 成功时会立即持久化并生成注入，并行会让世界读到旧档案。
- 没有引入新的 Actor Ledger、任务状态机、语义审查器、报告裁剪或滚动删除。
- 没有降低人物字段、必填完整度、原子提交、MVU 校验或世界语义推进要求。
- 没有修改三套冻结 vendor 原件，也没有把数据库、MVU、预设或 World Engine 的状态所有权并入 Doctor。

## 回归合同

- 修复后 MVU 的对象、数组、实际嵌套小队结构和正文 JSONPatch 人物路径都能触发完整补档。
- 正文只写“白露推门进来”、MVU 没有人物容器时，填表模型仍会发现并生成完整档案。
- 字段名、数组下标、软标题和玩家身份不会成为强制人物。
- 当前第 9 个及之后的新人不丢失；低输出上限会分批完成并只原子提交一次；同一精确人物提交在恢复时 0 次模型调用且不覆盖档案。
- 人物档案、收据与新报告都只有取得 IndexedDB 事务完成及只读事务读回后才算完整；聊天重载后完整字段可读并可导出，API 配置继续排除。
- 重 Roll 必须先撤销旧 swipe 的人物档案，再开始新分支发现；旧档案文本不得出现在新提示、当前分支存储、世界后台提示或公开注入中，切回各 swipe 时分别恢复各自档案。延迟保存期间再次重 Roll 或切换聊天时，新任务必须等待旧提交回滚，原聊天重开后仍保持切换前的正确分支。
- 冻结 World Engine 的真实 `MESSAGE_SWIPED` 与 `GENERATION_STARTED(regenerate)` 处理器必须在新正文落盘前选择生成前 checkpoint；捕获到的 `setExtensionPrompt` 应含 checkpoint 哨兵且不含被撤销分支的当前世界哨兵。
- 报告条目或诊断缺失必须在总览、按钮和导出文件中暴露，不能把不完整清单冒充完整；快速 B→C 切聊天或导出中切聊天不得串写状态。
- 桌面、390px 手机、低于 240px 的键盘可视区、动态视口、标签切换和聊天切换都不丢失未保存设置草稿。
