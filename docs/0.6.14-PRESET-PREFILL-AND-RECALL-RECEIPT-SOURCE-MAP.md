# 0.6.14 预填充末位与召回释放回执根因修复来源映射

状态：测试仓候选来源映射，不是正式验收结论。

## 真实故障链

1. 0.6.13 真实酒馆第 2 回合主生成已开始并结束，最终助手消息有 `</content>`、四选项和一个变量块，但缺少唯一的 `<content>` 开始标签；Doctor 在 `accepted-structure` 阶段正确拒绝，人物与世界均未写入。
2. 同一回合的 `generation:prepared` 真实记录显示世界召回包已准备 2 条公开投影，世界修订号为 1；正文结构失败后没有消费任何一条。
3. 失败释放回执却显示 `totalItemCount=0`、`messageId=0`。源码链表明这不是召回选择失败：`releaseSessionRecall` 没有把已预约包的条目数传给 `settleRecallPackage`，而后者用 `Number(null)` 把尚不存在的消息号变成了 0。
4. 配对预设的新增防全知 system 条目被追加在 Izumi assistant prefill 之后；因此 assistant prefill 不再是最后一个启用条目。第 1 回合偶然完整不能证明结构稳定，第 2 回合已经真实复现缺少开始标签和明显低于最低正文长度。

## 搜索后未移植的机制

- 故事神域的上下文围栏与窗口尾锚服务于独立侧聊分析窗口，不拥有 SillyTavern 主回复的 assistant prefill，也不拥有 Clean 的一次性召回包；直接移植会改变状态所有权。
- 数据库本体与表格模板的宽容解析、补填和原子提交用于独立填表，不参与主回复 prompt_order，也不拥有 Doctor 召回释放回执；本轮没有把数据库逻辑并入 Doctor。
- 旧 Doctor/2.0 的完整 provider cleanup、durable lease 与 consume proof 比 Clean 单入口复杂。本轮只复用“释放不等于消费、不得伪造消费身份”的已验证语义，不新建第二套编排器。

## 0.6.14 最小改动合同

1. 本地预设候选保留 247 个 prompts、214 个 order 条目；只修改 `user_lite_output_0825_v1` 的长度闭环文字，并移动一个既有 Doctor 防全知 order 条目；预设继续禁止上传。
2. `core.mjs::settleRecallPackage` 对缺失消息号保存 `null`，不再把 `null`/空串归一化为 0。
3. `index.js::releaseSessionRecall` 从当前 session 的已预约包写入真实条目总数与零消费数。
4. 补充针对空 messageId、实际条目数和运行时调用参数的回归；不降低任何档案、世界、变量或正文结构门槛。
