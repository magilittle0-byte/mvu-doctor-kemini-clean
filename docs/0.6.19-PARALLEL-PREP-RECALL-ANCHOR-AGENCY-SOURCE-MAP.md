# 0.6.19 来源映射：并行候选、召回锚点与玩家认知边界

## 真实故障路径

0.6.18 的真实候选在同一全新聊天第2回合再次超过120秒。脱敏阶段时间显示变量、人物、世界三个模型请求严格串行，三段模型耗时相加构成 Doctor 总耗时；这不是单个模型异常，也不能靠降低档案字段或删除世界推进解决。同回合独立核验还发现两项同根语义错误：模糊二元词组匹配把未精确落地的公开召回记成 `consumed`，正文叙述者用陈述句替玩家断言认知。

真实路径固定为：

`accepted-final → 变量审计/读回 → 人物候选/原子提交/读回 → 世界候选/事务提交 → 下一轮公开召回 → accepted-final精确消费回执`

## 本轮必须新写的宿主胶水

1. `acceptFinal` 的三个 Promise 调度和两个提交屏障必须按 Kemini Clean 现有函数签名、重试入口、状态面板及 session 取消语义重写；成熟2.0实现的P阶段对象不能直接移植。
2. 同回合新人物实际使用的票据序号不连续，世界准备阶段不能预猜 `profileId`。因此新写“稳定称谓候选 → 档案读回后的 name/aliases → 真实 profileId”解析，解析失败保持 `blocked_unready`。
3. 旧 recall 包没有锚点，因此保留完整公开片段的精确匹配兼容路径；任何模糊匹配都不再产生成功回执。
4. Izumi 的玩家认知边界没有现成可替换条目，本轮只在原输出与思维协议末尾追加窄规则，未修改第三方核心结构。

## 不变量

- 变量补丁只有独立审计、确定性重放、写入与读回成功后才算通过。
- 人物模型可以并行生成候选，但变量屏障前零写入；一批档案仍整体解析、整体校验、整体提交、整体读回。
- 世界模型可以并行准备候选，但人物读回屏障前零提交；人物尝试不等于世界裁决。
- 数据库继续独立填自己的表；Doctor 不接管数据库，预设不保存 Doctor 私有世界，MVU 不冒充人物档案生成成功。
- 本地快速检查不构成真实酒馆验收；运行代码或配对预设变化后必须从全新聊天重跑十二回合。
