# 第一阶段：分组材料先于唯一核对任务

2026-09-08，运行修改前来源映射。0.10.17 首轮已拒绝：医生真实修正姓名和客观天数，但承认存在对话对象后又以关系不重要为由漏登记，完整变量、界面和原生磁盘均空。没有删除本卡规则，现有任务也已经明确禁止增加重要性门槛，不能通过再加同义句冒充根因修复。

本轮重新全项目检索关系登记、系统实体、任务槽与组填表；完整读取当前输入组装、分组材料及原生发送，Story Oracle 的诊断任务构造与 callProfile，数据库角色/关系目标表、prepareAIInput/collectGroupFillResponse/统一提交调用，以及 SQL 提示构造、callCustomOpenAI 的材料替换和发送分支。Luna负责独立来源与实际出站核验。数据库自己的重要角色范围不移植到 MVU，未据此断言本次模型内部原因。

来源与最小适配：

- Story Oracle 的原生系统职责、最后用户诊断任务、模型路由和最小官方补丁继续保留。
- 本模块既有 `PHASE1_FINAL_DIAGNOSIS_TASK` 与 `PHASE1_CONTEXT_OWNERSHIP` 对原诊断的适配要求完整材料在前、唯一证据任务在最后。数据库按目标表先构造材料再送入任务提供结构参考；不复制数据库 SQL、角色重要性或独立写入机制。
- 当前分组在已含最后任务的基础消息后继续追加组路径与原规则，破坏了原有的材料/最终任务顺序。改为让既有 `composeDiagnosisMessages` 接收可选组材料，放在同一份 `EVIDENCE_INSTRUCTION` 之前。每组仍使用同一基线与全量材料，只调整位置，不复制提示、不新增规则。
- 必要新写仅为一个可选材料参数及既有调用接线。没有第二模型、消息截断、姓名/角色分类器、状态机或本地补丁执行器。

实际原生日志保留的五组请求与原构造消息逐字相同，目标模型与当前配置一致；失败第一组因环形日志窗口不再保留，没有将构造结果说成直接出站证据。只读定位随后在当前失败第一组上仅移动原任务，24908ms 返回中立关系登记且未提前写任务。完整输出已在本机通读，聊天、MVU和设置未变，补丁未执行。该结果只支持继续实测，不能计入验收或保证模型行为。
